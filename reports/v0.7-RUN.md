# The v0.7 pass

Run 2026-08-03 under `PROTOCOL-v0.7.md` and `PIN-v0.7-RUN.md`, against the predicate text and the
suite revision pinned before the work started.

## The blind number

**179 of 232.** Accepts 8/54, rejects 171/178.

That is the first run of a build implemented from the pinned spec text alone, and it is the number
the protocol commits to publishing whatever it turned out to be. It is a bad number and the reason
is worth more than the score.

## What went wrong, and it is one thing

42 of the 53 first-run mismatches carry one message: `aeeRunBinding does not equal the run binding
derived from this statement`. The build derived binding **version 1** while v0.7 carries **version
2**, and version 2 differs on two inputs the spec states plainly:

- `networkPosture` is the canonical digest of the **carried object**, not the value of that member's
  own `digest.sha256`. Version 1 left the `posture` string outside every signature.
- `observationVocabulary` becomes an input at all, so a narrowed `caught` set derives a different
  binding and every record then fails the comparison.

The miss is not that the text is unclear. It is in the Prerequisites section, in a single sentence
that spells the whole pre-image out member by member. The failure was one of reading method: the
implementation was driven from the changelog's list of what 0.7 adds, and the run binding is not on
that list, because it did not change **in 0.7**. It changed in the 0.6 revisions between the last
recorded run and this one, and a build that diffs rather than reads walks straight past it.

That is the finding this pass produced, and it belongs to the implementation rather than to the
spec: **an implementation working from a changelog is not a from-spec implementation.** A conformance
number bought that way measures whether the diff was legible, not whether the document is.

## The directed number

**231 of 232.** Accepts 54/54, rejects 177/178.

Everything after the first run is directed by the existing convention and none of it is evidence
that the text is determinate. Four families of rule were implemented after the number was recorded,
each read out of the spec rather than out of a vector:

| Fix | Vectors recovered |
|---|---|
| Run binding version 2 | 34 |
| `pass_indirect` as the recompute's third condition | 6 |
| Timestamp profile: uppercase `T` and `Z`, zone of `Z`/`+00:00`/`-00:00`, on both fields | 5 |
| Registered `networkPosture.posture` vocabulary, manifest attack-identifier floor, non-empty `signatures`, `attribution` as a substrate-row validity requirement | 7 |

One of these deserves naming separately. `aeeObservedAttacks` reads in one direction only: a seal
naming an attack obliges a caught row for it, and a seal omitting one licenses nothing. The suite
carries vectors that catch a reader assuming equality, and the author said so in the thread before
this run, so the correct implementation here is **directed and not evidence of anything**. It is
recorded as implemented, not as found.

## The open divergence

`bad-902-sealed-posture-ne-arming` is expected invalid and this build accepts it.

The reading behind that: the sealed record's kind constraints are the members it must carry
(`aeeStillArmed`, `aeeDropCount`, `aeePostureDigest`, `aeeObservedSet`, `aeeObservedAttacks`, and
`aeeMethod: intercepted`). Posture **equality** appears in the clean-row covering rule, where a seal
covers no clean row unless its posture digest equals the arming record's and the pinned one, and the
kind definition asks only that the seal carry `aeePostureDigest`, "the effective posture at run-end",
which is deliberately the value that may have moved.

So on this reading a mid-run posture flip yields a seal that satisfies its kind, covers no clean row,
and leaves a statement whose rows are all caught with nothing to fail on. If the intended reading is
that posture equality is a constraint of the kind rather than of the covering rule, the text could
say so where the kind is defined; if it is the covering rule and this vector's statement carries a
clean row, then the divergence is on this side.

Reported rather than resolved, because tuning the implementation until the vector passes is the one
thing this protocol exists to prevent.
