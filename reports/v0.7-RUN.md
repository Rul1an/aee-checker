# The v0.7 pass

Run 2026-08-03 under `PROTOCOL-v0.7.md` and `PIN-v0.7-RUN.md`, against the predicate text and the
suite revision pinned before the work started. Corpus `astrogilda/aee-conformance` at `84ba2271`;
spec `in-toto/attestation` at `23bee586`, specDigest `94de8da5…`, the commit `spec/VENDOR-PIN.json`
names and the head of PR #570.

Figures are stated against the corpus's own three dispositions. `vectors/MANIFEST.json` declares
**54 accept, 176 reject, 2 indeterminate**. An earlier draft of this report folded the two
indeterminate vectors into the rejects and wrote `/178`, which is a fraction of a corpus that does
not exist. Corrected throughout; the wrong denominator appears nowhere below.

## The blind number

**179 of 232.** Accepts 8/54, rejects 169/176, indeterminate 2/2.

The first run of a build implemented from the pinned spec text alone, and the number the protocol
commits to publishing whatever it turned out to be. It is a bad number and the reason is worth more
than the score.

## What went wrong, and it is one thing

42 of the 53 first-run mismatches carry one message: `aeeRunBinding does not equal the run binding
derived from this statement`. The build derived binding **version 1** while v0.7 carries **version
2**, which differs on two inputs.

The miss was mine, not the text's. An earlier draft of this report claimed the run binding "is not
on that list, because it did not change in 0.7", and drew a general lesson that an implementation
working from a changelog is not a from-spec implementation. That is refuted by the pinned spec
twice: the 0.6 changelog bullet (`spec-v0.7.md:1889-1900`) states both inputs verbatim, and the 0.7
bullet (`:2114`) says the binding "is unchanged and stays at version 2". The pointer was there. I
read "stays at version 2" and did not follow it back one bullet. The narrower, less flattering
finding is the true one, and the generalisation is withdrawn.

## The directed number

**232 of 232.** Accepts 54/54, rejects 176/176, indeterminate 2/2.

Directed, and not evidence about the determinacy of the text: it followed a spec diff already read
and, for one vector, an adversarial review of this implementation.

The blind run left 53 mismatches. Grouped by the message the blind build emitted, which is the only
partition the published run records support:

| Blind message | Vectors |
|---|---|
| `aeeRunBinding does not equal the run binding derived from this statement` | 42 |
| returned `valid` (no reason) | 7 |
| `carried result "pass_indirect" does not match the recomputed result "pass"` | 4 |
| **Total** | **53** |

An earlier draft published a per-fix attribution (43/5/3/2) and said it was counted from the run
records. It was not, and it cannot be: attributing a recovery to a particular fix needs a bisection
against the blind build, and the blind build is unrecoverable by this report's own admission below.
That table is withdrawn rather than restated. The four rules the directed pass implemented were the
run binding at version 2, the `pass_indirect` third condition, the `issuedAt` timestamp profile and
the manifest attack floor; which of the 53 each recovered is not established here.

Three rules implemented during the directed pass recovered **no vector at all**: the registered
`networkPosture.posture` vocabulary, non-empty `signatures`, and `attribution` as a substrate-row
validity requirement. No vector here was a blind mismatch on any of them, so their correctness in
this build is untested rather than confirmed.

One rule deserves naming separately. `aeeObservedAttacks` reads in one direction only: a seal naming
an attack obliges a caught row for it, and a seal omitting one licenses nothing. The suite carries
vectors that catch a reader assuming equality, and the author said so in the thread before this run,
so the correct implementation here is **directed and not evidence of anything**. It is recorded as
implemented, not as found.

## A defect this review found, and the vector that separates it

`bad-902-sealed-posture-ne-arming` was rejected by the blind build and *accepted* by the first
directed build. An earlier draft presented that as an open question of reading. It was not. It was a
regression introduced by the directed fixes, and the disqualifying test was written into that draft
without being run.

The covering rule reads, at `spec-v0.7.md:1291-1296`:

> A `sealed` record covers no clean row unless its `aeeStillArmed` is `true`, its `aeeDropCount` is
> zero or does not exceed an `aeeDropBound` declared in the same signed payload, and its
> `aeePostureDigest` equals **both the arming record's and** the pinned `networkPosture` digest…

The implementation compared the pinned conjunct and dropped the arming one — half of a sentence the
draft itself quoted. `bad-710` fails on the pinned comparison, so nothing else in the corpus exposed
the gap; `bad-902` is the single vector separating the two, its seal's posture correct against the
pin while a carried arming record disagrees. Fixed by carrying the posture of the arming records a row resolves into the covering check.

The scope of that quantifier is untested by this corpus and the report says so rather than implying
otherwise. Only four vectors carry more than one arming record and only `bad-902` gives them
divergent postures, where the offending record is referenced. A wider reading, ranging over every
carried arming record whether or not anything resolves it, scores an identical 232/232 here while
refusing constructed statements whose second arming record covers nothing — which would re-open, by
another door, the over-rejection the binding-version fix immediately below closes. The narrow
reading is taken because the rule says "the arming record's", definite and singular, and because a
record this document removes from consideration should not decide a covering question.

A second defect from the same review, at the wrong altitude rather than the wrong value: an
unimplemented `aeeBindingVersion` failed the whole statement, where `spec-v0.7.md:241-245` says a
verifier "reads it before deriving and rejects it fail-closed (the arming record covers nothing) …
distinguishably from a run-binding digest mismatch". It was also read *after* the binding
comparison, where a digest mismatch masks it. Both corrected, and the second only after a further review caught that it was not. The version is
read first, and an unimplemented value makes that record cover nothing rather than rejecting a
statement that may carry a second, valid arming record. Distinguishability was a separate defect: the
reason a record covers nothing was constructed and then discarded, so every such row was refused
under one generic message. That reason now reaches the refusal, which is what
`spec-v0.7.md:1327-1331` asks for by name on the covers-nothing kinds: `bad-980` and `bad-981` now
name `moat-drop` and `uncommitted-observation` rather than reporting as an unrecognized kind.

## Reason parity: what is measurable, and what is not

Verdict parity is what the numbers above report, and it is the weaker half. A reject naming the
wrong condition scores as agreement under it, which is the divergence class worth reporting, and it
is the half the corpus author asked for by name.

This implementation cannot supply it directly: it emits free prose and no condition codes, while the
corpus declares a 63-code vocabulary per vector in `expected.codes`, widened by
`expected.alsoCarries`. Scoring prose against codes needs a prose-to-code map, and a map is a
construction rather than a reading of the data. Two constructions over this same run disagreed
sharply — 175 of 178 from the script published here, 167 of 178 from an independent reviewer's — and
the disagreement is a fact about the constructions, not about the run. No single reason-parity
figure is claimed for that reason.

What is construction-independent is the shape of the ambiguity, and it is published as a script
(`scripts/reason_ceiling.py`) over two files anyone can fetch, so the numbers below are recomputable
rather than asserted:

| | |
|---|---|
| reject + indeterminate vectors | 178 |
| distinct reason strings this build emits | 136 |
| strings covering more than one declared condition | 5, over 17 vectors |
| corpus codes reachable from more than one string | 29 of 63 |
| best a per-string map can do under this construction | 175/178 |

The reading that matters is the last row against the third: this build's prose is close to
separating the corpus's conditions, and the residue is small and locatable rather than a wholesale
mismatch. An earlier draft said the divergence was "a real limitation rather than a labelling
accident" and cited two unpublished mappings to justify claiming nothing. Both halves were wrong:
the limitation is narrower than that sentence implied, and citing evidence a reader cannot recompute
is exactly the move this report should not make. The mappings are withdrawn; the script stands in
their place.

One substantive gap did close in review. `spec-v0.7.md:1327-1331` asks that a covers-nothing kind be
reported under a condition naming the kind rather than under the unrecognized-kind condition;
`bad-980` and `bad-981` are its vectors, and this build reported neither that way until the
distinguishability fix above. It does now.

The remaining fix is to emit condition codes, so a reason score needs no map at all.

## Indeterminate family

Both members pass under exactly one declared reading, **`positional`**: `ind-001` resolves to the
undecodable record, `ind-002` to the empty signature set, each naming the first fault in carried
order. Closure and coherence hold across the family, but they are asserted here by hand: the harness scores
verdicts only, so the `indeterminate 2/2` printed beside the accept and reject fractions is not
commensurate with them and should not be read as satisfying the corpus's three-part contract
mechanically. The reading is also confirmed across records only — intra-record fault ordering is not
exercised by this family. Naming the reading is the point — a pass here
without it says nothing about which permitted reading produced it.

different implementation. This breaks rule 6 of `PROTOCOL-v0.7.md`, the rule this run's own protocol
fixed in advance, and it is stated here rather than left to be found. A future blind pass commits the
build before running it.

## What this run is not evidence of

One implementation. Agreement between it and the reference rails is agreement between two readings,
not confirmation of either. Three implemented rules recovered no vector and are untested here.
No single reason-parity figure is claimed, and the ambiguity that prevents one is published as a
script rather than asserted. The directed number followed both a read spec diff and a review of this
build, so the only figure bearing on whether the text is determinate from a cold start is the blind
**179/232**.
